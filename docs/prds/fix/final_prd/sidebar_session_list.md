# Sidebar Session List Implementation PRD

## Core Guide (Within 200 lines, for immediate action)

### 1.1. Overview
- **Goal:** Implement a functional "Session List" in the Sidebar (`HistoryDrawer`) to allow users to switch, create, and delete chat sessions.
- **Non-Goal:** Session title editing (renaming), searching, or grouping.

### Detailed Requirements
- **[Must-have] Session Display:** List sessions showing `metadata.title` (priority) or truncated `session_id` (fallback), plus a relative timestamp (e.g., "2 hours ago").
- **[Must-have] Context Switching:** Clicking a session loads its history into the main chat view.
- **[Must-have] "New Chat" Action:** A fixed button to clear the current context. A new session ID is generated by the *backend* only after the first user message is sent (UI remains "clean" until then).
- **[Must-have] Deletion:** Ability to delete a session. If the *active* session is deleted, the UI must revert to a "New Chat" state.
- **[Must-have] Live Update:** The session list should refresh automatically when the drawer is opened or when a new session is effectively created.

### Implementation Plan

1.  **Context Layer (`chat-history-context.tsx`):**
    -   **Expose Refresh:** Export the internal `loadSessions` function (as `refreshSessions`) so the UI can trigger updates manually (e.g., on Drawer open).
    -   **Select Logic:** Ensure `selectSession(id)` correctly handles `id` changes and triggers `getChatHistory`.
    -   **New Session:** `createNewSession()` simply sets `currentSessionId = null` and clears `messages`.

2.  **UI Component (`history-drawer.tsx`):**
    -   **Structure:** Add a "New Chat" button pinned to the top or bottom.
    -   **List Item:** Render `Session` objects. Use `session.metadata.title || session.session_id` for the label.
    -   **Interaction:**
        -   `onClick` -> `selectSession(id)` & Close Drawer (optional, or keep open).
        -   `onDelete` -> `deleteSession(id)` -> `refreshSessions()` -> (If current) `createNewSession()`.

## Appendix (Detailed Reference)

### A. Detailed API Specifications
-   `GET /v1/stm/sessions`: Returns list. Key fields: `session_id`, `metadata.title`, `updated_at`.
-   `DELETE /v1/stm/sessions/:id`: Deletes session.

### B. Technical Dependencies Details
-   **State:** `historyList` in `ChatHistoryContext` is the source of truth.
-   **Safety:** Ensure switching sessions aborts or ignores any pending/streaming bot responses to prevent cross-session message leaks (out of scope for *this* fix, but keep in mind).

### C. Risk Analysis
-   **UUID UX:** Raw UUIDs are hard to read. *Mitigation:* Use `metadata.title` if available. If not, show first few chars of UUID or "Conversation [Date]".
-   **Stale List:** List might not show a just-created session. *Mitigation:* Trigger `refreshSessions` inside `handleStreamEnd` or when opening the drawer.

### D. Test Scenarios Details
-   **TC-1 (Display):** Open drawer -> See list of sessions with readable labels.
-   **TC-2 (Switch):** Click Session B -> Main Chat updates to Session B messages.
-   **TC-3 (Delete Active):** Delete the currently viewing session -> Main Chat clears (New Session state).
-   **TC-4 (New):** Click "New Chat" -> Chat clears. Send "Hello" -> Close/Open drawer -> New session appears in list.

## Virtual FGI Reflection & Intent Notes

-   **Developer Critique:** *"Does the list update when I talk?"* -> **Action:** Clarified that the new session only appears in the list *after* the first message is sent and persisted. The UI needs to refresh the list at that point (or next Drawer open).
-   **Designer Critique:** *"UUIDs are scary."* -> **Intent:** We prioritized `metadata.title`. Since we aren't building "Rename" yet, we assume the backend or a default "New Chat" title might be present, or we fallback gracefully.
-   **PM Critique:** *"What happens if I delete the active session?"* -> **Action:** added specific requirement to reset UI to "New Chat" state to prevent the user from staring at a "ghost" session.
